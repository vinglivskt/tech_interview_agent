# План внедрения режима «Собеседование» (устное интервью с разбором и оценкой)

Цель: добавить третий режим взаимодействия — «собеседование» — c живыми (свободными) ответами пользователя, последовательной подачей вопросов «от простого к сложному», разбивкой по темам, оценкой качества каждого ответа (в процентах) и финальной сводкой с сильными/слабыми сторонами и вердиктом по уровню.

Опираемся на существующую архитектуру VSA и уже реализованные фичи `chat` (общий диалог с RAG) и `quiz` (тестирование с вариантами ответов). Источник вопросов/ответов — существующий docx.

---

## 1) Архитектура и структура фичи

Добавляем вертикальный срез `sobesedovanie`:

```
app/features/sobesedovanie/
├─ api/
│  └─ router.py                 # /api/sobesedovanie/... (start, answer, results)
├─ domain/
│  ├─ models.py                 # Pydantic-модели запросов/ответов и доменные сущности
│  ├─ services.py               # Сервис сессии: выбор вопросов, оценка ответов, сводка
│  ├─ selection.py              # Алгоритм выбора вопросов по темам/уровню/«лестнице»
│  ├─ scoring.py                # Оценивание свободных ответов через LLM (проценты)
│  ├─ classification.py         # Классификация QA из docx по темам и уровням (LLM + кэш)
│  └─ repository.py             # Чтение QA из docx (повторное использование/обёртка)
└─ providers/
   └─ ... (при необходимости)
```

Интеграция в приложение:
- `app/main.py`: подключить новый роутер (`app.include_router(sobesedovanie_router, prefix="/api")`).
- `app/core/config.py`: параметры режима (см. ниже).
- `app/prompts/sobesedovanie/…`: промпты для классификации/оценивания/объяснений.

## 2) Формат источника данных (docx) и классификация

Имеющийся docx парсится через `app/features/chat/domain/interview_docx.py` → `InterviewQA(number, question, answer)`.

Новый режим требует тем и грейдов (junior/middle/senior). Возможные стратегии:
- Минимальный инвазивный путь: автоматически классифицировать каждый QA по темам и уровню через LLM при старте приложения и закэшировать.
- Кэш: `app/data/sobesedovanie_index.json` (создаётся автоматически). Включает:
  - `number`, `question`, `answer`
  - `topics: list[str]` (например: `python`, `db`, `networks`, `brokers`, `os`, `algorithms` и т.п.)
  - `level: "junior"|"middle"|"senior"`
  - `difficulty_score: float` (0.0–1.0 для внутриуровневой сортировки)
  - `doc_hash` для инвалидации кэша при изменении файла

Промпт-классификатор:
- Жёсткая схема JSON-ответа.
- Детёрминированные подсказки и пост-валидация.
- Повтор при невалидном JSON (до N попыток с уточняющей инструкцией).

## 3) Режим «лестницы» (от простого к сложному) и покрытие тем

Параметры по умолчанию (можно вынести в конфиг):
- Уровни: `junior`, `middle`, `senior`.
- Количество вопросов:
  - `junior`: 15–18
  - `middle`: 18–22
  - `senior`: 22–25
- Темы: определяются автоматически на шаге классификации; используем фиксированный список предустановленных тем + «other».

Алгоритм подбора:
1) Отфильтровать QA по требуемому уровню (либо по точному совпадению, либо с допуском соседних уровней при нехватке).
2) Разбить по темам, гарантировать минимальное покрытие тем (например, 4–6 тем минимум за сессию, с ротацией: python → db → networks → brokers → … → python → …).
3) Внутри каждой темы сортировать по `difficulty_score` по возрастанию, чтобы идти «лестницей» от простого к сложному.
4) Перемежать темы по кругу, постепенно повышая сложность, пока не достигнем требуемого количества вопросов для уровня.
5) Детализация сложности внутри уровня: `difficulty_score` позволяет подбирать более простые и более сложные вопросы в рамках одного грейда.

Fallback’и:
- Если для какой-то темы не хватает вопросов на уровне — добираем из соседних уровней (вниз для junior, вверх для senior) с пометкой в метаданных.
- Жёсткий максимум на повтор одной темы подряд (например, не более 2 подряд).

## 4) Свободные ответы, оценка (проценты) и объяснения

Поток:
- Пользователь отвечает в свободной форме.
- LLM сравнивает ответ пользователя с эталонным (`InterviewQA.answer`). Выдаёт:
  - `score_percent` (0–100): доля покрытых ключевых тезисов и точности формулировки.
  - `covered_points` / `missed_points` (массивы тезисов).
  - `techlead_explanation`: краткое объяснение «как техлид» (что правильно/что упущено; без воды).
- Порог засчёта вопроса: `>= 50%`.
- Баллы за вопрос: равны проценту (`score_percent`) — копим суммарный «процентный» счёт и отдельно считаем количество «зачтённых» вопросов.

Инварианты и защита качества:
- Нормализуем/очищаем ответы от мусора (markdown, эмодзи, «Источники: …» — как уже делается при сохранении в docx).
- Запрашиваем LLM в строгом JSON-формате (схема), с повтором при невалидном ответе.
- Ограничиваем длину объяснения и формулируем тон (строго, по делу).

---

## 5) Финальная сводка и вердикт

После 15–25 вопросов формируем:
- Процент правильных (>=50%) и средний `score_percent` по всем вопросам.
- Перечень вопросов с краткой оценкой и объяснением.
- Сильные стороны: топ-3 темы с наивысшим средним `score_percent`.
- Зоны роста: топ-3 темы с наименьшим средним `score_percent` + рекомендации.
- Вердикт по уровню (эвристика):
  - Junior, если средний `score_percent` ≤ 60% и/или засчитано ≤ 60% вопросов.
  - Middle, если 60–80%.
  - Senior, если > 80% и стабильно покрыты «сложные» вопросы в нескольких темах.
- Отдельно выдаём перечень тем/подтем, которые стоит подтянуть (короткие actionable-пункты).

Вердикт формируем гибридно:
- Правило + короткий LLM-комментарий (1–2 предложения, без самоуверенных утверждений, но с чёткими рекомендациями).

## 6) API контракты

- `POST /api/sobesedovanie/start`
  - Вход: `{ "level": "junior|middle|senior", "topics?": ["python", "db", ...] }` (topics — опционально для приоритезации).
  - Выход: `{ "session_id", "question": { "id", "text", "topic", "level", "number" }, "total_planned" }`.

- `POST /api/sobesedovanie/answer`
  - Вход: `{ "session_id", "question_id", "user_answer": "..." }`.
  - Выход: `{ "score_percent", "is_counted": true|false, "techlead_explanation", "covered_points": [...], "missed_points": [...], "next_question?": {...}, "is_last": bool }`.

- `GET /api/sobesedovanie/results/{session_id}`
  - Выход: `{ "level_requested", "verdict_level", "summary": { "counted": N, "total": M, "avg_percent": X }, "strengths": [...], "weaknesses": [...], "by_topic": [{ "topic", "avg_percent", "count" }], "details": [ { "question_text", "topic", "score_percent", "explanation" } ] }`.

Все ответы содержат минимально достаточные поля для фронта, без разглашения сырых LLM-промптов.

## 7) Промпты и обработка LLM

Директория: `app/prompts/sobesedovanie/`:
- `classification.md` — определяет темы, уровень и difficulty_score для QA.
- `scoring.md` — строгое сравнение ответа пользователя с эталоном → JSON со схемой.
- `verdict.md` — краткий комментарий «техлида» по итогу (без повторов уже подсчитанных метрик).

Правила:
- Явная JSON-схема в каждом промпте и проверка парсинга.
- Повтор с уточняющей инструкцией при невалидном JSON (до 2–3 попыток).
- Тон ответов: деловой, по существу, на русском.

## 8) Конфигурация (`app/core/config.py`)

Добавить поля:
- `sobes_topics`: список поддерживаемых тем (по умолчанию: `python, db, networks, brokers, os, algorithms, patterns, testing, devops, security, other`).
- `sobes_counts_by_level`: `{ junior: [15,18], middle: [18,22], senior: [22,25] }`.
- `sobes_pass_threshold_percent`: `50` (засчёт вопроса).
- `sobes_cache_path`: `app/data/sobesedovanie_index.json`.
- `sobes_max_explanation_len`: например `600` символов.

Опционально: флаги для отладки (`sobes_debug_prompts`, `sobes_retries`).

---

## 9) Состояние и хранение сессий

Аналогично `QuizSessionStore`:
- `SobesSessionStore`: TTL-кеш на N часов, хранит список выбранных вопросов (с метаданными), прогресс, ответы пользователя, проценты.
- Память процесса (in-memory). Персист не обязателен.

Структуры:
- `SobesQuestion`: `{ id, number, text, topic, level, difficulty_score }`.
- `SobesAnswerRecord`: `{ question_id, user_answer, score_percent, is_counted, explanation, covered_points, missed_points }`.

## 13) Риски и допущения

- Docx не содержит явных меток уровней/тем — используем LLM-классификацию с кэшем (детерминизм за счёт строгих промптов и пост-валидации).
- Эталонные ответы могут быть длинными/развёрнутыми — в `scoring` ограничиваемся ключевыми тезисами и кратким объяснением.
- Если какой-то темы не окажется в базе — алгоритм gracefully деградирует (уведомление в метаданных/логах + добор из других тем/уровней).
