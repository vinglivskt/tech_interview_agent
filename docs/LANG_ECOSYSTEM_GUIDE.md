# LangChain, LangGraph и LangSmith — простое объяснение на примере проекта

Это руководство объясняет, зачем нужны три технологии и что именно они делают в `tech_interview_agent`.

| Технология | Простыми словами | Где помогает в проекте |
|---|---|---|
| **LangChain** | Единый набор адаптеров и инструментов для работы с LLM | Все вызовы генерации и Ollama-эмбеддингов; структурированные результаты скоринга; деление документов на части |
| **LangGraph** | Движок сценариев, состоящих из шагов, пауз, переходов и сохраняемого состояния | Многошаговое интервью по системному дизайну |
| **LangSmith** | Журнал запусков LLM для отладки и анализа качества | Просмотр запросов и ответов модели, поиск проблем в промптах, подготовка датасетов для оценок |

Одна аналогия: **LangChain — инструменты, которыми приложение обращается к модели; LangGraph — план и память интервью; LangSmith — журнал, по которому разработчик разбирает, как прошло обращение к модели.** Они работают вместе, но не выполняют одну и ту же работу.

## Как это связано с приложением

Приложение принимает вопрос или ответ кандидата, формирует запрос к языковой модели (LLM), получает ответ и превращает его в результат для API и интерфейса. Для этого нужно решить три разные задачи:

1. Вызвать разные модели одинаковым способом и, где требуется, получить проверяемые данные, а не произвольный текст.
2. Провести интервью, которое длится через несколько HTTP-запросов и должно помнить текущий шаг.
3. Дать разработчику возможность выяснить, что именно отправили модели и как она ответила.

В проекте эти задачи распределены между LangChain, LangGraph и LangSmith.

## LangChain — единый способ работать с моделями

### Обычный ответ модели

Без общего адаптера приложение само собирало бы HTTP-запросы к каждому провайдеру, отдельно разбирало бы ответы и поддерживало особенности каждого API. LangChain предоставляет модели с единым интерфейсом: передать сообщения через `ainvoke()` и получить ответ модели.

В проекте обычная генерация тоже выполняется через LangChain:

- Ollama обслуживается `ChatOllama` в `backend/src/features/chat/providers/ollama.py`.
- OpenCode Zen использует OpenAI-совместимый `ChatOpenAI` в `backend/src/features/chat/providers/opencode.py`.
- Интерфейс приложения к провайдерам остаётся общим — `LLMGateway`; для OpenCode эмбеддинги отдельно предоставляет Ollama.

Например, чат может вызвать `llm.generate(messages, tags=["answer"])`. Для бизнес-логики это простой интерфейс; внутри выбранный адаптер конвертирует сообщения в формат LangChain и вызывает свою модель через `ainvoke()`. Прямого HTTP-вызова к API генерации у старого клиента больше нет.

### Структурированный ответ: вместо текста — объект с полями

Предположим, модель должна оценить ответ кандидата. Если попросить её написать свободный текст, программа должна угадать, где в нём балл, объяснение и список ошибок. Если попросить вернуть JSON, JSON всё ещё может оказаться сломанным или содержать неподходящие значения.

Structured output решает эту задачу так: мы задаём Pydantic-схему, а LangChain просит модель вернуть ответ, соответствующий этой схеме. В проекте схемы определены в `backend/src/core/structured.py`:

- `ScoreResult` — процент, сильные и пропущенные пункты, пояснение для обычного собеседования;
- `DesignScore` — балл, пять категорий рубрики, сильные и пропущенные пункты, пояснение;
- `ClassificationBatch` — список классификаций вопросов в объектной оболочке `items`.
- `WrongAnswers` — ровно три ошибочных варианта ответа для квиза.

Вызов по смыслу выглядит так:

```python
result = await llm.generate_structured(
    messages,
    schema=ScoreResult,
    temperature=0.2,
    tags=["scoring"],
)
```

На выходе `result` — валидированная Pydantic-модель с полями вроде `result.score_percent`, а не строка, которую надо вручную разбирать. Схема проверяет и нормализует форму данных: например, ограничивает оценку диапазоном и ограничивает число пунктов в списках. Она не проверяет, справедливо ли модель оценила смысл ответа.

Так устроены структурированные задачи: оценка ответа на собеседовании (`sobes/domain/scoring.py`), пакетная классификация вопросов (`sobes/domain/classification.py`), генерация неправильных вариантов квиза (`quiz/domain/quiz_generator.py`) и оценка шагов системного дизайна (`design/domain/graph.py`). Для Ollama используется `ChatOllama.with_structured_output`; для OpenCode — соответствующий метод LangChain `ChatOpenAI`.

### Что происходит, если модель или сеть не ответили

У приложения остался безопасный резервный результат, но больше нет обходного вызова старого API и ручного парсинга JSON:

- неудачный structured-вызов возвращает `None`;
- скоринг собеседования возвращает безопасный нулевой результат;
- классификация использует нейтральные значения (`other`, `middle`, `0.5`);
- системный дизайн повторяет structured-запрос до трёх раз, затем возвращает стандартную ошибку оценки.

Это не попытка получить «надёжность» ценой скрытой смены технологии: путь вызова остаётся одним и тем же — через LangChain. При этом LangChain не устраняет недоступность модели и не гарантирует истинность её ответа.

### Эмбеддинги и нарезка документов

Для поиска по материалам RAG приложению нужны эмбеддинги — числовые представления текста, по которым Qdrant ищет похожие фрагменты. Они создаются через `OllamaEmbeddings` в том же LangChain-адаптере Ollama.

Перед индексированием документ разбивается на чанки. `backend/src/features/chat/domain/vectorization.py` использует `RecursiveCharacterTextSplitter`: он старается делить сначала по абзацам и строкам, а затем по предложениям и пробелам. Это даёт поиску небольшие полезные фрагменты вместо одного длинного документа.

OpenCode Zen не предоставляет эмбеддинги, поэтому при выборе OpenCode для генерации приложение всё равно обращается к Ollama за эмбеддингами. Вызов эмбеддингов при этом также проходит через LangChain.

### Где LangChain используется постоянно

В текущем проекте LangChain — основной маршрут для **всех вызовов генерации и Ollama-эмбеддингов**, а не включаемая опция только для скоринга. Обычные ответы чата, квиза и обогащения вопроса идут через `ChatOllama` или `ChatOpenAI`; места, которым нужны поля и типы данных, используют structured output. Настройки `LLM_STRUCTURED_OUTPUT` больше нет.

## LangGraph — сценарий, который ждёт кандидата и продолжает работу

### Узлы, переходы и состояние

Представьте инструкцию интервьюеру: «Сначала выясни требования. Когда кандидат ответит — оцени ответ и переходи к архитектуре. Потом дождись ответа ещё раз». Это не один непрерывный вызов: пользователь отвечает через отдельные HTTP-запросы.

LangGraph описывает такой процесс как:

- **узел (node)** — действие, например шаг интервью и его оценка;
- **переход (edge)** — какое действие выполнить дальше;
- **состояние (state)** — текущий шаг, предыдущие ответы, подсказки и результаты;
- **прерывание (interrupt)** — пауза в ожидании ответа пользователя;
- **чекпоинтер (checkpointer)** — сохранение состояния, чтобы граф можно было продолжить.

### Пример: «Спроектируй URL Shortener»

Реализация находится в `backend/src/features/design/domain/graph.py`, а `DesignService` связывает граф с API.

```text
Старт → Уточнение требований → Архитектура → Данные → Масштабирование → Компромиссы → Конец
            ждёт ответ         ждёт ответ
```

Когда сессия запускается, граф доходит до узла текущего шага. Узел вызывает `interrupt()` и отдаёт приложению информацию о вопросе. Кандидат отвечает на `/api/design/answer`; сервис возобновляет граф с тем же `session_id` как `thread_id` и передаёт ответ через `Command(resume=ответ)`. Узел просит LangChain оценить ответ по `DesignScore`, сохраняет результат в состояние и граф переходит к следующему шагу.

В настройках `DESIGN_CHECKPOINTER=postgres` означает сохранение чекпоинтов в PostgreSQL. Если инициализировать его не удалось, код использует `MemorySaver`; в режиме `memory` состояние хранится только в памяти процесса. Поэтому переносимый между рестартами API вариант зависит от доступности инициализации PostgreSQL.

### Что даёт LangGraph

- Вместо ручного управления длинным сценарием граф явно описывает шаги и порядок выполнения.
- Ожидание пользователя встроено в процесс, а не имитируется удержанием одного запроса открытым.
- Продолжение привязывается к идентификатору сессии; состояние хранится в чекпоинтере.
- Можно отдельно определить логику узлов и переходов, не меняя публичный контракт API.

LangGraph не задаёт оценки и не делает сам интервью лучше: содержание и скоринг по-прежнему принадлежат промпту, модели и правилам приложения. В проекте граф применяется к режиму системного дизайна, а не ко всем разделам приложения.

## LangSmith — разбор вызовов LLM

Если модель неожиданно поставила низкий балл, итоговой цифры мало. Нужно посмотреть, какой контекст попал в запрос, что ответила модель и к какой функции относился вызов. LangSmith записывает такие запуски и позволяет изучать их по проекту, тегам и метаданным.

Интеграция находится в `backend/src/core/langsmith.py` и провайдерах `backend/src/features/chat/providers/`. Вызовы добавляют метаданные вроде `feature`, `scenario_id`, `session_id` и теги вроде `scoring`. Это помогает отфильтровать трассы и исследовать конкретный случай.

Условная запись для дизайн-скоринга выглядит так:

```text
Провайдер/модель: OpenCode / выбранная модель
Режим и шаг: design / уточнение требований
Вход: критерии шага, история и ответ кандидата
Выход: балл, рубрика, объяснение
```

Трассировка выключена по умолчанию (`LANGSMITH_TRACING=false`). Чтобы отправлять её в LangSmith, настройте `LANGSMITH_TRACING=true` и `LANGSMITH_API_KEY`; `LANGSMITH_PROJECT` выбирает имя проекта. Без ключа трассировка отключается с предупреждением, но вызовы LangChain продолжают работать.

Трассы могут содержать пользовательские ответы и промпты. Включайте отправку с учётом того, кто имеет доступ к аккаунту и куда отправляются данные. LangSmith помогает видеть и сравнивать поведение, но не исправляет промпт автоматически.

### Эвалы — проверка изменений на примерах

`backend/src/training/langsmith_eval.py` подготавливает примеры в формате «вопрос и ответ кандидата → ожидаемая оценка и пояснение» и умеет загрузить их в датасет LangSmith. Такой набор полезен, когда меняется промпт скоринга: можно повторно прогнать старые примеры и увидеть, как изменились результаты.

Это заготовка процесса, а не автоматическое знание правильного ответа. Польза эвалов зависит от качества примеров и ожидаемых оценок.

## Как технологии сотрудничают в одном ответе

Кандидат отвечает на шаге системного дизайна:

1. **LangGraph** находит приостановленную сессию и продолжает граф с ответом.
2. Узел формирует контекст шага и вызывает общий LLM-интерфейс.
3. **LangChain** обращается к настроенному провайдеру и возвращает валидированный `DesignScore`.
4. LangGraph записывает оценку и переводит интервью на следующий шаг.
5. **LangSmith**, если включён и настроен ключ, записывает вызов модели для последующего разбора.

Запомните короткую формулу: **LangChain вызывает модель и приводит результат к нужной форме; LangGraph ведёт многошаговый процесс; LangSmith показывает разработчику, как прошли вызовы модели.**
