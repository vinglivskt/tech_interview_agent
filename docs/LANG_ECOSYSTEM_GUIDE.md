# LangChain, LangGraph и LangSmith — простое объяснение на примере проекта

Этот документ объясняет три технологии не как рекламные названия, а через задачи, которые они решают в `tech_interview_agent`. Сначала короткая версия:

| Технология | Простыми словами | Задача в проекте |
|---|---|---|
| **LangChain** | Инструменты, которые помогают обращаться к языковым моделям и получать от них данные в удобной форме | Попросить модель вернуть ответ по проверяемой схеме; аккуратно делить документы на части для поиска |
| **LangGraph** | Исполнитель сценариев, состоящих из шагов и переходов между ними, с сохранением состояния | Вести интервью по системному дизайну: задать шаг, дождаться ответа, оценить и перейти дальше |
| **LangSmith** | Место, где можно посмотреть записи запусков LLM и сравнивать их | Разобраться, какой запрос ушёл модели, что она вернула и как меняется качество после правки промпта |

Удобная аналогия: **LangChain — инструменты интервьюера; LangGraph — план и память самого интервью; LangSmith — видеозапись и журнал для разбора интервью командой разработки.** Это не три названия одного и того же. Они могут работать вместе, но решают разные задачи.

## Сначала — что происходит без этих названий

Приложение принимает ответы кандидата, отправляет контекст в LLM (языковую модель), использует ответы в режимах собеседования, чата, квиза и системного дизайна, а также индексирует материалы для поиска. Модель отвечает обычным текстом. Этот текст нужно встроить в приложение: распознать оценку, объяснение, следующие шаги и так далее.

Здесь появляются три разных инженерных вопроса:

1. **Как надёжно получить от модели данные нужного формата?** Это одна из задач LangChain.
2. **Как провести длинный сценарий из нескольких шагов и не потерять, на каком мы месте?** Это задача LangGraph.
3. **Как понять, что именно приложение отправляло модели и почему получилось такое качество?** Это задача LangSmith.

## LangChain: удобная работа с моделью и форматом ответа

### На пальцах

Без структурного вывода модель может вернуть оценку как текст: «Кандидат хорошо разобрал требования, я бы поставил 78 баллов». Программе приходится угадывать, где число, а где объяснение. Это похоже на получение заполненной от руки анкеты, в которой каждый раз по-разному расположены поля.

LangChain позволяет описать форму ответа и попросить модель заполнить её. В нашем проекте форма задаётся Pydantic-схемами: например, `ScoreResult` описывает процент оценки, покрытые и пропущенные пункты, а `DesignScore` дополнительно задаёт оценки по рубрике системного дизайна. Полученный ответ можно проверить как данные, а не разбирать догадками из произвольного текста.

### Пример: оценка ответа на техническом собеседовании

Путь находится в `backend/src/features/sobes/domain/scoring.py`, схемы — в `backend/src/core/structured.py`, а вызов модели — в `backend/src/features/chat/providers/ollama.py`.

Упрощённо происходит следующее:

```python
result = await llm.generate_structured(
    messages,
    schema=ScoreResult,
    tags=["scoring"],
)

if result is None:
    # Запасной вариант: обычный текстовый вызов и прежний разбор JSON
    text = await llm.generate(messages, format="json")
```

Это иллюстрация реальной идеи, не полный фрагмент функции: рабочий код также передаёт параметры вызова, метаданные для трассировки и обрабатывает результат по существующим правилам.

Что происходит по шагам:

1. Сервис собирает инструкции для модели и ответ кандидата.
2. При включённой настройке структурного вывода `OllamaClient` просит LangChain вызвать `ChatOllama.with_structured_output` с Pydantic-схемой.
3. Ответ превращается в объект нужной формы. Например, у оценки есть числовое поле и отдельные списки сильных и слабых пунктов.
4. Если structured-вызов не сработал, функция возвращает `None`, и вызывающий код использует существующий запасной разбор JSON с повторными попытками.

В проекте предусмотрены схемы для оценки собеседования, оценки системного дизайна и пакетной классификации вопросов. Валидаторы нормализуют некоторые значения и ограничивают размеры полей; для рубрики дизайна проверяется набор ключей.

### Это не обязательно включено целиком

Важно различать два уровня, реализованные в проекте:

- Скоринговые вызовы передают Ollama параметр `format="json"` и без включения расширенного структурного вывода. Он просит вернуть JSON, чтобы прежний парсер мог его прочитать.
- Путь LangChain `with_structured_output` включается настройкой `LLM_STRUCTURED_OUTPUT=true`. По умолчанию она выключена. Если путь не справился, приложение возвращается к legacy-разбору.

Значит, «LangChain установлен» не означает, что все ответы всего приложения всегда идут через LangChain. Интеграция добавлена точечно там, где важен надёжный формат скоринга. Клиентские провайдеры имеют свои реализации; проверяйте конкретную настройку и путь вызова перед тем, как ожидать одинаковое поведение от каждой модели.

### Ещё один пример: нарезка текста для поиска

`backend/src/features/chat/domain/vectorization.py` использует `RecursiveCharacterTextSplitter`. Перед индексированием длинный документ нужно разделить на небольшие фрагменты: при вопросе поиск сможет найти подходящий кусок, а не отправлять модели весь документ.

Сплиттер сначала старается резать по крупным смысловым границам: абзацам, строкам, предложениям и затем пробелам. Поэтому короткие и длинные документы удобнее разбивать, чем простым разрезанием каждых N символов. После этого код объединяет небольшие куски, где это возможно, сохраняя прежний контракт `chunk_text`.

**Что даёт LangChain здесь:** готовую утилиту разбиения и стандартный способ структурировать взаимодействие с LLM. **Чего сам по себе он не делает:** не улучшает автоматически качество модели, не гарантирует правильность смысла и не заменяет правила приложения. Схема проверяет форму и часть ограничений, но не может доказать, что оценка кандидата справедлива.

## LangGraph: управление многошаговым интервью

### На пальцах

Если попросить обычную функцию провести интервью целиком, она должна как-то дождаться ответа человека между шагами. Запросы HTTP приходят раздельно: сначала приложение показывает вопрос, затем пользователь отправляет ответ отдельным запросом. Между этими запросами надо сохранить состояние: сценарий, текущий шаг, ответы и использованные подсказки.

LangGraph описывает процесс как граф. **Узел (node)** делает один шаг работы; **ребро (edge)** говорит, куда идти после него; **состояние (state)** хранит данные, нужные всему процессу. В системном дизайне узел соответствует шагу интервью, а граф между HTTP-запросами приостанавливается и возобновляется.

### Пример: интервью «Спроектируй URL Shortener»

Основной код — `backend/src/features/design/domain/graph.py`; сервис, который связывает граф с API, — `backend/src/features/design/domain/services.py`.

Упрощённая схема:

```text
Старт → Уточнение требований → Архитектура → Данные → Масштабирование → Компромиссы → Конец
             ⏸ ждём ответ          ⏸ ждём ответ
```

При первом запросе сервис создаёт сессию и запускает граф. Текущая нода доходит до `interrupt()` — точки остановки — и отдаёт шаг клиенту. Когда кандидат отправляет ответ на `/api/design/answer`, сервис возобновляет тот же граф через `Command(resume=ответ)`. Нода оценивает ответ, добавляет результат в состояние и граф переходит дальше.

Для идентификации продолжающейся сессии используется `thread_id`, равный `session_id`. Чекпоинтер сохраняет состояние по этому идентификатору. Настройка `DESIGN_CHECKPOINTER` задаёт вариант хранения: PostgreSQL позволяет хранить чекпоинты вне памяти процесса; `memory` хранит их в памяти. При ошибке настройки PostgreSQL в коде предусмотрен переход на `MemorySaver`, поэтому поведение при аварийном фолбэке отличается от нормального PostgreSQL-режима.

### Что конкретно получаем

- Понятное описание последовательности работы вместо ручного управления переходами по индексам в бизнес-логике.
- Остановку на ожидании ответа и продолжение того же сценария на следующем запросе.
- Хранение ответов, номера шага и подсказок в состоянии графа.
- Возможность хранить это состояние в PostgreSQL, чтобы оно не зависело только от памяти конкретного процесса API.
- Сохранение существующего API режима системного дизайна: граф используется внутри сервиса, а не требует менять интерфейс для пользователя.

LangGraph **не оценивает ответ сам по себе**. За оценку по-прежнему отвечает LLM и код скоринга; граф определяет, когда спросить, когда оценить и куда перейти. Он также не означает, что все режимы приложения уже переведены на граф: описанный граф используется для режима системного дизайна.

## LangSmith: журнал запусков и работа с качеством

### На пальцах

Когда модель неожиданно поставила низкий балл, одного итогового ответа мало, чтобы понять причину. Полезно посмотреть, какой промпт и контекст отправили, что вернула модель, сколько занял вызов и к какому режиму или сессии он относился. LangSmith собирает такие записи (traces/runs) для анализа.

В проекте шлюз находится в `backend/src/core/langsmith.py`, а интеграция вызовов — в клиентах LLM, например `backend/src/features/chat/providers/ollama.py`. Вызовы могут передавать метаданные вроде режима, сценария и `session_id`, а также теги вроде `scoring`. Это помогает фильтровать трассы и связывать запись с конкретной задачей.

### Что увидит разработчик

Для одного вызова трасса полезна как карточка разбора:

```text
Режим: design       Сценарий: url-shortener       Тег: scoring
Запрос модели: контекст шага + предыдущие ответы + ответ кандидата
Результат: оценка, рубрика, объяснение
```

Точная доступность полей зависит от провайдера и пути вызова. LangSmith помогает обнаружить, например, что в запрос не попал предыдущий ответ, модель вернула некорректную структуру или правка промпта изменила оценки. Это инструмент наблюдения и отладки, а не автоматический гарант качества.

### Настройка и ограничения

В конфигурации проекта трассировка выключена по умолчанию (`LANGSMITH_TRACING=false`). Для отправки записей нужно включить её и задать `LANGSMITH_API_KEY` (либо `LANGCHAIN_API_KEY`). Имя проекта задаётся `LANGSMITH_PROJECT`, по умолчанию — `tech-interview-agent`. При включённой настройке без API-ключа код пишет предупреждение и отключает трассировку. При выключенной трассировке SDK импортируется лениво и вызовы идут обычным путём.

Трассы могут содержать промпты, пользовательские ответы и контекст. Поэтому при использовании внешнего сервиса следует осознанно настроить, какие данные разрешено туда отправлять, и использовать соответствующий аккаунт/endpoint проекта. Само наличие переменной `LANGSMITH_ENDPOINT` в примере конфигурации не превращает LangSmith в локальное хранилище автоматически.

### Эвалы — следующий этап работы с трассами

`backend/src/training/langsmith_eval.py` содержит код для формирования примеров датасета и отправки их в LangSmith. Входом служат записи ответов, из которых собираются пары «вопрос и ответ кандидата → ожидаемая оценка и пояснение». Такой набор можно использовать для повторной проверки скоринга после изменения промпта.

Это заготовка для оценки качества, а не магический механизм, который сам узнает правильные оценки. Чтобы сравнение было полезно, нужны репрезентативные примеры и качественные ожидаемые оценки. Результат эвалы помогает увидеть различия; решение о приемлемом качестве остаётся за командой.

## Как они работают вместе в одном примере

Кандидат отвечает на шаге системного дизайна:

1. **LangGraph** знает, какая нода сейчас ожидает ответ, и возобновляет сессию после HTTP-запроса.
2. Узел скоринга собирает контекст шага и отправляет его модели.
3. **LangChain**, если `LLM_STRUCTURED_OUTPUT=true` и провайдер поддерживает этот путь, просит вернуть результат по схеме `DesignScore`. Если он не сработал, используется запасной разбор JSON.
4. Граф сохраняет оценку и ответы в своё состояние и открывает следующий шаг.
5. **LangSmith**, если включён и настроен ключ, записывает вызов модели с метаданными, чтобы разработчик мог позже его исследовать.

Это совместная работа, но обязанности не смешиваются: LangGraph ведёт процесс, LangChain формирует удобный для программы результат, LangSmith помогает разработчику наблюдать и проверять качество.

## Как понять, включена ли технология у вас

| Что проверить | Где | Что означает |
|---|---|---|
| `LLM_STRUCTURED_OUTPUT` | `.env` / настройки приложения | Включает путь structured output LangChain; по умолчанию `false` |
| `LANGSMITH_TRACING` и API-ключ | `.env` / окружение | Включают отправку трасс в LangSmith; без ключа она отключится |
| `DESIGN_CHECKPOINTER` и доступность PostgreSQL | `.env`, логи старта | Определяют, где сохраняется состояние графа дизайна; при ошибке возможен фолбэк в память |
| `chunk_text` | `backend/src/features/chat/domain/vectorization.py` | Сплиттер LangChain используется кодом индексации текста |

## Короткий итог

- **LangChain** полезен приложению в конкретных местах: оформить ответ LLM в проверяемую структуру и нарезать текст для RAG. Он не заменяет бизнес-правила и не гарантирует истинность ответа.
- **LangGraph** полезен там, где есть длительный сценарий с паузами и состоянием. В проекте это интервью по системному дизайну.
- **LangSmith** полезен разработчикам для просмотра вызовов модели и последующего сравнения скоринга на примерах. Пользовательское интервью может работать и без него.

Если запомнить одну фразу: **LangChain помогает получить ответ в нужной форме, LangGraph помнит и проводит по шагам, LangSmith помогает увидеть, что происходило внутри вызова модели.**
